# Lab 3 — AI Use and Reflection

This document details the artificial intelligence tools, models, and key prompts utilized throughout the TokTickIT Lab 3 engineering sprint.

## 1. LLMs and Agents Used

Across the Lab 3 sprint, we adopted a structured spec-driven development workflow utilizing multiple AI coding assistants:

1. **Specification & Contract Review Agent**:
   - **Model**: Claude Sonnet 3.5 / Claude Sonnet 4.5
   - **Role**: Used for translating handout requirements into formal engineering specifications (FR/BR/AC numbering, authorization matrices), identifying contractual ambiguities across specification/API/UI/test documents, resolving cross-document conflicts, and conducting multi-round contract audits prior to implementation.
2. **AI Coding & Implementation Agent**:
   - **Model**: Antigravity Coding Assistant powered by Gemini 3.5 Flash / Gemini 3.8 Flash
   - **Role**: Used for test-driven development (TDD), generating failing Vitest API and React Testing Library component tests, implementing full-stack authentication features across Express/Prisma and React/TypeScript, conducting database migrations, and producing completion verification reports.
3. **Diagnostic & State Audit Agent**:
   - **Model**: Claude Sonnet 4.5 (Kiro IDE)
   - **Role**: Used for comprehensive system-state audits (git status, test infrastructure diagnosis, database consistency verification), DATABASE_URL configuration debugging, and producing unabridged terminal output verification when test-count discrepancies emerged.

## 3. My Reflection

Using multiple specialized AI agents with explicit handoff boundaries enabled a disciplined contract-first development workflow throughout Lab 3. Having the specification agent (Claude) first review and stress-test the engineering contracts (`specification.md`, `api-spec.md`, `ui-spec.md`, and `tests.md`) across three rounds before any code was written surfaced critical conflicts that would have shipped as security gaps — most notably the authorization-matrix contradiction where Administrator access to Internal Notes was simultaneously permitted and forbidden in different tables. The verbatim-quote requirement (rather than trusting "already consistent, no conflicts found" summaries) was essential to catching this.

The coding agent (Antigravity/Gemini) was strong at TDD discipline when explicitly instructed to write failing tests first, and demonstrated good judgment when refusing to drop the `requester_users` table early (correctly explaining it would break Lab 2 regression). However, **the most important lesson from Lab 3 was learning that an AI agent's markdown summary of test results — however well-formatted, confident, or internally-consistent — is not trustworthy evidence on its own.** The Issue #4 fabricated-test-count incident (where per-file counts were generated from memory rather than counted from actual terminal output, with errors masked because the fabricated numbers coincidentally summed to the correct total) required establishing a new verification protocol: every "N/N passing" claim must be checked against either raw, unabridged terminal output or a diff against the previous issue's known-good per-file baseline before being accepted.

The diagnostic agent (Kiro/Claude) proved invaluable for infrastructure troubleshooting — the DATABASE_URL configuration bug (quoted value in `.env` causing Prisma validation failure) was diagnosed and fixed systematically through comprehensive state audit (git status, database queries, file content verification, fresh test execution) rather than speculative fixes. Most importantly, adopting an "audit first, trust nothing" approach and requiring complete unabridged terminal output for manual line-by-line verification prevented wasting time when test infrastructure itself was broken, and caught test-count discrepancies from stale cached output (Login: 4→5, MyTickets: 9→8) that would otherwise have gone unnoticed.

**Takeaway for future sprints:** Agent-produced summaries are starting points for investigation, not final evidence. Critical claims (test counts, security properties, contract consistency) require independent verification through primary sources (raw terminal output, actual file content, database queries) before being accepted as fact.
